Executes a shell command in the workspace directory with optional timeout.

The tool name is legacy: Unix commands run under /bin/sh, NOT the user's
login SHELL. Windows uses ComSpec/cmd, not PowerShell. Use portable syntax or
invoke an explicitly available interpreter for its own syntax; do not assume
PIPESTATUS, arrays, [[ ... ]] or pipefail exist in /bin/sh. sysinfo reports the
actual default command shell. A pipeline's last exit code is not proof that
all earlier commands passed; prefer direct assertion-test processes.

CRITICAL — tool selection rules. Do NOT use `bash` when a dedicated tool exists:
Optional tools may be deferred rather than present in the current schemas. If a
dedicated file-management or HTTP tool below is not visible, first use tool_search
to discover its exact schema. Discovery does not expand permissions. If your
role cannot discover or use it, report that limit instead of routing around it.
- Read files → use `read` (NEVER cat/head/tail/type/Get-Content)
- Search contents → use `grep` (NEVER bash grep/rg)
- Find files → use `glob` (NEVER bash find/ls/dir)
- Write files → use `write` (NEVER echo/cat heredoc)
- Edit files → use `edit` (NEVER sed/awk)
- Move or rename → use `move` (NEVER mv)
- Copy → use `copy` (NEVER cp)
- Delete → use `remove` (NEVER rm) — it moves the target to .kkcode/trash so it can be restored
- Create directories → use `mkdir` tool (NEVER bash mkdir)
- Archive → use `archive` (NEVER bash tar/zip)
- HTTP requests → use `http_request` for anything beyond a plain page fetch, `webfetch` to read a page
  (NEVER curl/wget/Invoke-WebRequest)

These are not style preferences. The dedicated tools validate paths against the workspace
boundary (including symlink escapes), refuse protected files such as .git and shell rc files,
make deletion recoverable, and apply the egress checks that block internal addresses and cloud
metadata endpoints. Going through `bash` skips every one of those.

Only use `bash` for: git, npm, pip, docker, make, cargo, go, python, node, and other system
commands — including `python3`/`node` one-liners for data processing (CSV/JSON aggregation and
similar), which is the intended path for that work.

Parameters:
- command (required): shell command to execute
- timeout (optional): finite process deadline in ms; command default 120000/max 600000,
  service default 600000/max 3600000. Waiting never extends this deadline.
- lifetime (optional): command (default) or service. Use service for one temporary
  foreground development server; pass cwd/env separately, without shell operators
  or redirections. Strict runs use a bounded test that owns its services instead.
- yield_time_ms (optional): wait 0–30000ms before returning a managed task handle.
  The process keeps running after this wait; use task_output with wait_ms/cursor.
- description (optional): human-readable description of what this command does. For simple commands keep it brief (5-10 words). For complex commands (piped commands, obscure flags), add enough context to clarify.
- run_in_background (optional): return a task handle immediately unless a yield
  window is requested. lifetime: service already selects managed backgrounding.
  The launch receipt reports the effective deadline, cwd and task identity.

Rules:
- Always quote file paths that contain spaces with double quotes.
- Use lifetime: service for temporary servers/watchers and task_stop to request
  graceful shutdown; verify the actual exit with task_output. A POSIX service
  must handle SIGTERM and exit normally. Force-stop, lost output and incomplete
  cleanup remain subject to inspection; stopping does not roll back effects.
- Run final project checks after owned services have closed. A background launch
  or a successful readiness probe is not a complete verification receipt.
- Use description to explain non-obvious commands.
- When issuing multiple independent commands, make multiple bash calls in parallel.
- When commands depend on each other, chain with && (e.g. `git add . && git commit -m "msg"`).
- NEVER use interactive flags like -i (e.g. git rebase -i, git add -i) — they require interactive input which is not supported.

- On POSIX, do not append shell `&` and return while children keep running. Explicit unjoined launches are rejected before execution, including when run_in_background is also set. Use a bounded test harness that closes and joins its services, or remove the shell `&` and launch one finite managed background command. Explicitly joined parallel work (`... & wait`) remains available; actual child lifetime is still checked. CMD's single `&` is sequential and does not use this POSIX rule.

# Completion verification

After authorized changes, run the project's real tests/builds through this tool.
For bespoke file, document or API checks, create an assertion test with write/edit
in the authorized workspace and run `node --test <explicit-test-file>` or
`python3 -m unittest <test-module>`. A false assertion must fail the process.
Completion observes direct test processes after the last change. Repeating a
shell condition or printing PASS does not supply a recognized verification receipt.
Do not mask errors with pipes, redirection, `;` or `|| true`; use `&&` for dependent checks.
Long output is archived automatically when needed. Use artifact_read / artifact_search
on the returned archive instead of appending tail/grep to the test command.
When repairing a check, preserve its arguments, module list, working directory and
environment. Rerun a failed && group together in its original order; separately
passing members do not replace the original group receipt.
Keep rerunnable test scripts. Do not append deletion/cleanup to a check command;
changes after the check require another actual check of the final state.
Syntax/whitespace checks prove only syntax/whitespace, not the requested behavior.
Read-only/Plan tasks must not create or edit files just to obtain a check receipt.
For temporary test servers, prefer an assertion-test harness that starts its own
services, waits for readiness, checks behavior, closes services in finally and
joins all children before exiting with the real test result. Do not use pkill to
clean up unbounded servers. Background cancellation/timeout is not rollback or
test acceptance; stop and report any owner-inspection requirement rather than
replaying effects or acknowledging on the owner's behalf.

# Committing changes with git

Only create commits when requested by the user. If unclear, ask first. When creating a git commit:

1. Run in parallel:
   - `git status` (NEVER use -uall flag)
   - `git diff` to see changes
   - `git log --oneline -5` to follow commit message style

2. Analyze changes and draft a concise commit message focusing on "why" not "what".
   Do NOT commit files that likely contain secrets (.env, credentials.json, etc.).

3. Stage and commit:
   - Prefer `git add <specific-files>` over `git add -A` or `git add .`
   - ALWAYS pass the commit message via a HEREDOC:
     git commit -m "$(cat <<'EOF'
     Commit message here.

     Co-Authored-By: kkcode <noreply@kkcode.dev>
     EOF
     )"
   - Run `git status` after commit to verify success

4. Git safety rules:
   - NEVER update git config
   - NEVER run destructive commands (push --force, reset --hard, checkout ., clean -f, branch -D) unless user explicitly requests
   - NEVER skip hooks (--no-verify) unless user explicitly requests
   - NEVER force push to main/master — warn the user
   - ALWAYS create NEW commits rather than amending, unless user explicitly asks for amend
   - When a pre-commit hook fails, the commit did NOT happen — fix the issue, re-stage, create a NEW commit (do NOT --amend)
   - NEVER commit unless the user explicitly asks

# Creating pull requests

When creating a PR:
1. Run in parallel: git status, git diff, check remote tracking, git log + git diff <base>...HEAD
2. Analyze ALL commits and draft PR title (under 70 chars) and summary
3. Push and create PR:
   gh pr create --title "title" --body "$(cat <<'EOF'
   ## Summary
   <1-3 bullet points>

   ## Test plan
   - [ ] testing checklist...
   EOF
   )"
4. Return the PR URL

# Read-only execution boundary

Plan/read-only work permits only argument-checked inspections. Per-command environment overrides and options that launch preprocessors, external diffs, text conversion or other helpers are not read-only, even if the executable name is normally a reader. Use dedicated read/grep/glob tools when possible. Safe Git inspections use a host-controlled executable/argv/environment with repository helpers, pagers, fsmonitor and optional index writes disabled; an unavailable safe invocation must not fall back to an ordinary shell command. This classification assumes trusted host executables and is not an OS sandbox.
