Create and manage a structured task list for tracking multi-step work. This helps you track progress, organize complex tasks, and demonstrate thoroughness to the user. It also helps the user understand the progress of your work.

## When to Use This Tool

Use this tool proactively in these scenarios:

1. **Complex multi-step tasks** — When a task requires 3 or more distinct steps or actions
2. **Non-trivial tasks** — Tasks requiring careful planning or multiple operations
3. **User provides multiple tasks** — When users provide a list of things to be done (numbered or comma-separated)
4. **After receiving new instructions** — Immediately capture user requirements as todos
5. **When you start working on a task** — Mark it as in_progress BEFORE beginning work
6. **After completing a task** — Mark it as completed and add any follow-up tasks discovered during implementation

## When NOT to Use This Tool

Skip using this tool when:
1. There is only a single, straightforward task
2. The task is trivial and tracking provides no benefit
3. The task can be completed in less than 3 trivial steps
4. The task is purely conversational or informational

NOTE: Do NOT use this tool if there is only one trivial task. Just do it directly.

## Examples of When to Use

User: I want to add a dark mode toggle to the application settings. Make sure you run the tests when done!
→ Create todo list:
  1. Create dark mode toggle component in Settings page
  2. Add dark mode state management (context/store)
  3. Implement theme styles for dark mode
  4. Update existing components to support theme switching
  5. Run tests and fix any failures

Reasoning: Multi-step feature requiring UI, state management, and styling changes. User explicitly asked for tests.
</example>

User: Help me rename the function getCwd to getCurrentWorkingDirectory across my project
→ First search to understand scope, then create todo list with one item per file that needs updating.

Reasoning: Multiple files affected, systematic tracking prevents missing any occurrence.
</example>

→ Create todo list breaking down each feature into specific tasks.

Reasoning: User provided multiple complex features in a list.
</example>

## Task States and Management

Task states: pending, in_progress, completed, blocked, cancelled. These are authored planning states, not observed verification results. The list is durable and belongs to the current session and agent, including in Plan mode; updating it does not authorize project-file writes.

IMPORTANT — Task descriptions must have two forms:
- content: imperative form describing what needs to be done (e.g. "Run tests", "Fix authentication bug")
- activeForm: present continuous form shown during execution (e.g. "Running tests", "Fixing authentication bug")

Rules:
- Update task status in real-time as you work
- Mark tasks complete IMMEDIATELY after finishing (don't batch completions)
- Multiple independent tasks may be in_progress when they are actually being worked on concurrently
- Preserve the returned stable id when updating an existing task, and send the returned expectedRevision for subsequent updates
- A stale revision is rejected: inspect the returned conflict or use todo_read for current session state before replanning; never blindly replay an old list
- Prefer mode: merge for incremental updates: omitted items keep their state and
  order. Use replace only for a deliberate replacement plan; its omitted
  unfinished own tasks become cancelled, while completed history remains.
- Explain blocked/cancelled or replanned work with reason. Preserve returned IDs;
  an unknown ID does not create a task. Read the returned snapshot before retrying.
- Only edit this agent's own items; dependencies may name existing same-session item IDs
- Evidence references may identify actual same-session messages or parts; they do not grant execution authority or prove acceptance passed

## Task Completion Requirements

- ONLY mark a task as completed when you have FULLY accomplished it
- If you encounter an unresolved blocker, use blocked; use cancelled only when the task is deliberately discontinued
- When blocked, create a new task describing what needs to be resolved
- Never mark a task as completed if:
  - Tests are failing
  - Implementation is partial
  - You encountered unresolved errors
  - You couldn't find necessary files or dependencies
- A completed task or count of completed tasks is NOT proof of passing tests. Report observed commands, outputs and acceptance results separately, including failed, missing and unknown results.

## Task Breakdown Guidelines

- Create specific, actionable items
- Break complex tasks into smaller, manageable steps
- Use clear, descriptive task names
- Always provide both forms:
  - content: "Fix authentication bug"
  - activeForm: "Fixing authentication bug"

When in doubt, use this tool. Being proactive with task management demonstrates attentiveness and ensures you complete all requirements successfully.

## Parameters

- todos (required): array of task objects
  - id: stable returned ID for an existing task; omit for a new task
  - content (required): task description in imperative form
  - status (required): "pending" | "in_progress" | "completed" | "blocked" | "cancelled"
  - activeForm: present continuous form shown during execution
  - dependencies: existing todo IDs in this session
  - evidenceRefs: existing conversation references as {kind: "message" | "part", id: "..."}; no paths, foreign session IDs, or verified flags
- expectedRevision: revision from the previous returned snapshot (the host captures the initial revision before model execution)
- mode: merge (recommended for partial changes) or replace (legacy default)
- todos[].reason: optional explanation, up to 512 characters
