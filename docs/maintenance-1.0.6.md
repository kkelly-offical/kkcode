# 面向 1.0.6 的存量修复评议

日期：2026-09-26。此记录对应独立修复分支，不是1.0.6发布说明。
从main `8efcb34`开始，未混入待审核的1.0.5文档PR #23；本轮不调整发行版本、打tag或发布。

## 第一轮：配置读写与跨端提示

提交 `acaa256`；对应 [Issue #24](https://github.com/kkelly-offical/kkcode/issues/24)。

- 确认旧权限字段／无效权限规则会导致整个配置层被丢弃，模型配置从界面消失；
  保存只校验已清洗的有效视图，可能写入仍然无效的原始配置并报告成功。
- 改为保留有效的模型、Agent等配置，整个无效权限子树不应用；错误解除前暂停工具和扩展启动。
- 禁止用Yolo、缓存审批、项目／环境高优先级覆盖解除拦截。解析失败、含糊错误路径和
  无效安全策略也不能因回退默认值放宽执行权限。
- 保存前校验实际落盘对象；失败保留原文件并返回中文说明。旧字段给出手动迁移路径，
  不自动把旧`allow`转换成更宽的有效权限。
- Web/Android设置面板显示安全诊断，模型列表仍可见；错误原值和私密路径不进入诊断响应。
  诊断只在主动打开设置后出现，原按键布局不变。

第二轮对该修复补查了缓存放行、扩展启动、错误来源、密钥脱敏和原文件不变的负控。
随后复审保存边界时增加两个先失败的用例：合法`null`空文档应能继续配置；YAML的
`false`／`0`不能被当成空对象并悄悄覆盖。解析现与加载器一致，只有`null`／空文档归一为空配置。
恢复路径复审还发现延迟执行、直接loop和重新信任绕过了普通boot入口的检查：现统一
在初始化之前检查，已启动内核也不能跳过。新增真实内核回归证明先拒绝且零模型请求，
修正后同一句柄恢复；如果项目层仍错误，合法用户配置可保存并明确提示执行仍暂停，
不在保存之后因重启扩展失败误报“未保存”。
协议说明见[配置诊断](remote-command-contract.md#配置诊断面向106的修复尚未发行)。

## 第二轮：主动落盘与定时回调竞态

提交 `04b9adb`。此前文档PR的[Windows检查](https://github.com/kkelly-offical/kkcode/actions/runs/36029637169/job/107734816907)
在`loop-integration`结束清理时出现`ENOTEMPTY`，不是README断言失败。

- 已排队的自动flush可能在`flushNow()`完成后重新创建进程锁文件，干扰退出／清理。
- 给定时任务增加代次检查，在获取锁（会创建文件）之前拒绝过时任务；干净状态不重复写盘。
- 公开合成调度回归在原版产生2次后续锁写入而失败，修复版只有显式读取需要的1次而通过。
  没有增加删除重试、延长等待或关闭Windows用例来掩盖竞态。
- 多进程写入、工作根隔离、部分历史替换及原回合生命周期回归保留。
