# 严格任务的独立代码审查

严格验收不再把工作区 `.kkcode/review-state.json` 当作审查通过证据。候选中的代码可以控制该文件，因此其中的 `approved` 标记不能代表宿主或用户的审批。

每次封存候选后，宿主使用 `runIndependentReview` 运行一个**没有工具、没有写入接口**的模型请求。默认采用当前会话模型，也遵守显式配置的 `models.roles.review` 和数据出域限制；不静默切换供应商。

## 输入与覆盖

- 从冻结基线读取修改、增加、删除的完整文件清单，包含未跟踪文件；通过受控 Git 禁用 Hook、外部 diff、textconv 和过滤程序。
- 每项提供完整修改前／后文本，明确放入不可信内容边界。文件中的角色标记、命令和“请批准”文字不具有指令权限。
- 首批安全上限为 100 个变更文件、单文件 64 KiB、总投影 256 KiB。二进制、私密路径、超限或不可读内容返回 `unknown`，不截断后宣称完整审查。
- 模型必须逐项返回精确文件名和覆盖声明。缺项、重复、额外文件、非法 JSON、工具调用、取消或模型错误均不能批准。
- 存在 critical/high 问题时，即使模型填写 approved，也强制转换为 changes_requested。

## 回执与真实权限

宿主对有效报告生成内存品牌回执，绑定 manifest、候选指纹、验收合同、完整清单及模型／端点凭据作用域指纹。序列化模型 JSON 或工作区文件不能伪造该品牌。凭据只参与私密作用域指纹，不写入回执。

模型报告仅是独立代码审查辅助：不能替代构建、测试或用户人工确认，不能授予发布和合并权限。严格门禁只有拿到对应当前候选的宿主回执才可能通过。重启后应对当前候选重新运行审查，不将任意磁盘 JSON 重新解释成可信回执。

人工判据另行绑定候选内容、验收标准与策略。候选变化会清除旧人工确认；等待用户确认期间候选发生变化时，该确认不应用到新内容。

## 验证范围

`test/independent-review.test.mjs` 覆盖真实 Git 投影、完整 before/after 清单、无工具模型请求、完整覆盖检查、问题升级、候选变化、超额／二进制及工作区伪造审查拒绝。`test/ultra-host-acceptance.test.mjs` 覆盖实际 Ultra 流程和人工确认竞态。

这些是受控模型 fixture 验证，不是实付模型质量基准。覆盖清单证明输入和报告范围完整，不证明模型不会漏报代码缺陷。
